= Configure credentials for model downloads

[role="_abstract"]
You can configure credentials to enable model download jobs to authenticate with private model registries such as Hugging Face Hub or S3-compatible storage.
Without valid credentials, download jobs fail with authentication errors when accessing gated or private models.

.Prerequisites

* Model caching is enabled in the `inferenceservice-config` ConfigMap.
* The job namespace (default: `kserve-localmodel-jobs`) exists.
* You have the required authentication tokens or access keys for the private model registry.

.Procedure

Model caching supports two credential mechanisms: service account credentials and storage spec credentials.
Choose the mechanism that matches your environment.

[discrete]
=== Option 1: Use service account credentials

. Create a secret containing the model registry credentials in the job namespace.
+
The following example creates a secret for Hugging Face Hub:
+
[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: hf-secret
  namespace: kserve-localmodel-jobs
  annotations:
    serving.kserve.io/s3-endpoint: ""
    serving.kserve.io/s3-usehttps: ""
type: Opaque
stringData:
  HF_TOKEN: <your_hugging_face_token>
----
+
Replace `<your_hugging_face_token>` with your Hugging Face Hub access token.

. Create or patch a service account in the job namespace that references the secret:
+
[source,yaml]
----
apiVersion: v1
kind: ServiceAccount
metadata:
  name: hf-model-cache-sa
  namespace: kserve-localmodel-jobs
secrets:
  - name: hf-secret
----

. Reference the service account in the `LocalModelCache` resource:
+
[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: LocalModelCache
metadata:
  name: gated-model-cache
spec:
  sourceModelUri: "hf://meta-llama/Meta-Llama-3-8B-Instruct"
  modelSize: 20Gi
  nodeGroups:
    - worker-group-1
  serviceAccountName: hf-model-cache-sa
----

[discrete]
=== Option 2: Use storage spec credentials

. Create a credential secret in the job namespace:
+
[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: storage-config
  namespace: kserve-localmodel-jobs
type: Opaque
stringData:
  hf-credentials: |
    {
      "type": "hf",
      "token": "<your_hugging_face_token>"
    }
  s3-credentials: |
    {
      "type": "s3",
      "bucket": "<bucket_name>",
      "region": "<region>",
      "access_key_id": "<access_key>",
      "secret_access_key": "<secret_key>"
    }
----
+
Replace the placeholder values with your actual credentials.

. Reference the storage key in the `LocalModelCache` resource:
+
[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: LocalModelCache
metadata:
  name: s3-model-cache
spec:
  sourceModelUri: "s3://my-bucket/models/my-model"
  modelSize: 50Gi
  nodeGroups:
    - worker-group-1
  storage:
    key: s3-credentials
----

[discrete]
=== Option 3: Use a ClusterStorageContainer for URI-prefix-based injection

You can configure a `ClusterStorageContainer` resource with `workloadType: localModelDownloadJob` to automatically inject a container spec with embedded credentials for download jobs matching a specific URI prefix.

. Create a `ClusterStorageContainer` that matches the model URI prefix:
+
[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: ClusterStorageContainer
metadata:
  name: hf-download-container
spec:
  container:
    name: storage-initializer
    image: kserve/storage-initializer:latest
    env:
      - name: HF_TOKEN
        valueFrom:
          secretKeyRef:
            name: hf-secret
            key: HF_TOKEN
    resources:
      requests:
        memory: 100Mi
        cpu: 100m
      limits:
        memory: 1Gi
        cpu: "1"
  supportedUriFormats:
    - prefix: "hf://"
  workloadType: localModelDownloadJob
----
+
The `workloadType` field must be set to `localModelDownloadJob`.
Only `ClusterStorageContainer` resources with this workload type are considered for model cache download jobs.

.Verification

. After creating a `LocalModelCache` with credentials, monitor the download job:
+
[source,terminal]
----
$ oc get jobs -n kserve-localmodel-jobs
----

. If the download job fails with an authentication error, check the job logs:
+
[source,terminal]
----
$ oc logs job/<job_name> -n kserve-localmodel-jobs
----
+
Replace `<job_name>` with the name of the failed download job.

.Troubleshooting

If download jobs fail with authentication errors:

* Verify that the credential secret exists in the correct namespace (the job namespace, not the model namespace).
* Verify that the token or access key is valid and has not expired.
* Verify that the service account is correctly associated with the secret.
* For `ClusterStorageContainer` credentials, verify that the `workloadType` is set to `localModelDownloadJob` and the URI prefix matches the model URI.
