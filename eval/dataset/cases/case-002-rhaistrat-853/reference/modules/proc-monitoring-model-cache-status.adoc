= Monitor model cache status

[role="_abstract"]
You can monitor model cache download progress at three levels: cache level, node level, and job level.
Monitoring download status helps you confirm that models are available on target nodes before deploying inference services.

.Prerequisites

* At least one `LocalModelCache` or `LocalModelNamespaceCache` resource exists.

.Procedure

[discrete]
=== Check cache-level status

. View the overall status of a model cache, including per-node download status and the number of available copies:
+
For a cluster-scoped `LocalModelCache`:
+
[source,terminal]
----
$ oc get localmodelcache <cache_name> -o yaml
----
+
For a namespace-scoped `LocalModelNamespaceCache`:
+
[source,terminal]
----
$ oc get localmodelnamespacecache <cache_name> -n <namespace> -o yaml
----

. Check the `status.nodeStatus` field to see the download status on each node:
+
[source,terminal]
----
$ oc get localmodelcache <cache_name> -o jsonpath='{.status.nodeStatus}' | python3 -m json.tool
----
+
.Example output
[source,json]
----
{
    "worker-0": "NodeDownloaded",
    "worker-1": "NodeDownloading",
    "worker-2": "NodeDownloadPending"
}
----

. Check the `status.copies` field to see aggregate counts:
+
[source,terminal]
----
$ oc get localmodelcache <cache_name> -o jsonpath='{.status.copies}' | python3 -m json.tool
----
+
.Example output
[source,json]
----
{
    "available": 1,
    "total": 3,
    "failed": 0
}
----
+
The model is fully cached when `available` equals `total` and `failed` is `0`.

The following table describes the `NodeStatus` values:

.`NodeStatus` values
[cols="1,3", options="header"]
|===
|Status
|Description

|`NodeNotReady`
|The node is not yet available for downloading. The node may be offline or the agent pod may not be running.

|`NodeDownloadPending`
|The download job has been created but has not started. The job may be waiting for pod scheduling or resource availability.

|`NodeDownloading`
|The download is actively in progress. For large models, this can take several minutes.

|`NodeDownloaded`
|The model has been successfully cached on this node.

|`NodeDownloadError`
|The download failed on this node. Check the download job logs for error details.
|===

[discrete]
=== Check node-level status

. View the download status of all models on a specific node:
+
[source,terminal]
----
$ oc get localmodelnode <node_name> -o jsonpath='{.status.modelStatus}' | python3 -m json.tool
----
+
Replace `<node_name>` with the name of the cluster node.
+
.Example output
[source,json]
----
{
    "llama-3-8b-cache": "ModelDownloaded",
    "team-a/mistral-cache": "ModelDownloading"
}
----
+
For cluster-scoped caches, the status key is the model cache name.
For namespace-scoped caches, the status key uses the format `namespace/cacheName`.

The following table describes the `ModelStatus` values:

.`ModelStatus` values
[cols="1,3", options="header"]
|===
|Status
|Description

|`ModelDownloadPending`
|The download job has been created but has not started.

|`ModelDownloading`
|The download is actively in progress.

|`ModelDownloaded`
|The model has been successfully cached.

|`ModelDownloadError`
|The download failed. Check the job logs for details.
|===

[discrete]
=== Check job-level status

. List download jobs in the job namespace:
+
[source,terminal]
----
$ oc get jobs -n kserve-localmodel-jobs
----

. View the logs of a specific download job:
+
[source,terminal]
----
$ oc logs job/<job_name> -n kserve-localmodel-jobs
----
+
Replace `<job_name>` with the name of the download job.
+
Download job names follow the pattern `<modelName>-<nodeName><random-suffix>`.

[NOTE]
====
Completed download jobs are automatically cleaned up after the time specified by the `jobTTLSecondsAfterFinished` ConfigMap parameter, which defaults to 3600 seconds (1 hour).
If you need to inspect job logs after this period, increase the TTL value in the ConfigMap before creating the cache.
====
