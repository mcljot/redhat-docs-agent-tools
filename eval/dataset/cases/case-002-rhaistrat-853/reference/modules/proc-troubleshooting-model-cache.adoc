= Troubleshoot model cache issues

[role="_abstract"]
You can diagnose and resolve common model cache issues by checking download job logs, verifying storage configuration, and understanding the on-disk storage layout.
This procedure covers the most common failure modes and their resolutions.

.Procedure

[discrete]
=== Diagnose download failures

. Check the model cache status to identify nodes with errors:
+
[source,terminal]
----
$ oc get localmodelcache <cache_name> -o jsonpath='{.status.nodeStatus}' | python3 -m json.tool
----
+
Nodes with `NodeDownloadError` status indicate a failed download.

. View the download job logs for the affected node:
+
[source,terminal]
----
$ oc get jobs -n kserve-localmodel-jobs -l model=<model_name>,node=<node_name>
$ oc logs job/<job_name> -n kserve-localmodel-jobs
----
+
Replace `<model_name>` with the name of the model cache, `<node_name>` with the affected node name, and `<job_name>` with the name of the download job.

. Verify that the LocalModelNode agent DaemonSet pod is running on the affected node:
+
[source,terminal]
----
$ oc get pods -n kserve -l control-plane=kserve-localmodelnode-agent -o wide | grep <node_name>
----

[discrete]
=== Common failure modes and resolutions

.OOMKilled storage initializer

*Symptom*: The download job pod is terminated with `OOMKilled` status.

*Cause*: The model size exceeds the container's memory limits. The default download container has a memory limit of `300Mi`.

*Resolution*: Configure a `ClusterStorageContainer` with higher resource limits for the download job container, or update the storage initializer configuration to increase the default resource limits.

.Path misalignment between PV and DaemonSet

*Symptom*: The model downloads successfully but is not detected by the agent, or the model is downloaded to the wrong location.

*Cause*: The `local.path` in the `LocalModelNodeGroup` PersistentVolume spec does not match the `hostPath` configured in the LocalModelNode agent DaemonSet.

*Resolution*: Verify that the `local.path` value in the PV spec matches the DaemonSet `hostPath` volume mount.
The default DaemonSet hostPath is `/models`.
The DaemonSet mounts this path to `/mnt/models` inside the container, and models are stored in `/mnt/models/models/<storageKey>/` subdirectories.

.Permission errors on host directory

*Symptom*: The download job fails with permission denied errors when writing to the local storage.

*Cause*: The host directory ownership does not match the `fsGroup` configured in the `inferenceservice-config` ConfigMap.

*Resolution*: Verify that the host directory (for example, `/models`) is owned by the UID and GID matching the configured `fsGroup` value.
For example, if `fsGroup` is `1000`:
+
[source,terminal]
----
$ ssh <node_name> "sudo chown 1000:1000 /models"
----

.PVC binding failures

*Symptom*: The download job pod is stuck in `Pending` status because the PVC cannot bind to a PV.

*Cause*: The PVC storage class, capacity, or access modes do not match the PV spec in the `LocalModelNodeGroup`.

*Resolution*: Verify that the `persistentVolumeClaimSpec` in the `LocalModelNodeGroup` matches the `persistentVolumeSpec`.
Check that the `storageClassName`, `accessModes`, and `resources.requests.storage` values are compatible.

.Credential errors

*Symptom*: The download job fails with authentication or authorization errors such as `401 Unauthorized` or `403 Forbidden`.

*Cause*: The credentials are missing from the job namespace, the token has expired, or the service account is not correctly associated with the credential secret.

*Resolution*:

* Verify that the credential secret exists in the job namespace (default: `kserve-localmodel-jobs`), not in the model cache's namespace.
* Verify that the `serviceAccountName` in the `LocalModelCache` spec matches a service account in the job namespace that has access to the credential secret.
* For `ClusterStorageContainer` credentials, verify that the `workloadType` is set to `localModelDownloadJob`.
* Verify that the token or access key is valid and has not expired.

.Failed download job not retried automatically

*Symptom*: A download job has failed but no new job is created.

*Cause*: Failed download jobs are not automatically retried.
The agent limits the total number of jobs per model per node to 2 to prevent excessive retries.

*Resolution*: Fix the underlying issue (credentials, permissions, or network), then delete the failed job to trigger a new download attempt:
+
[source,terminal]
----
$ oc delete job <job_name> -n kserve-localmodel-jobs
----
+
The agent creates a new download job during its next reconciliation cycle.

=== Storage key mapping and disk layout

On-disk folder names for cached models are SHA-256 hashes of the `sourceModelUri`, not human-readable model names.
The agent uses the first 16 hexadecimal characters of the hash as the folder name.

To map a model cache to its on-disk folder:

. Compute the storage key for a model URI:
+
[source,terminal]
----
$ echo -n "hf://meta-llama/Meta-Llama-3-8B-Instruct" | sha256sum | cut -c1-16
----
+
.Example output
[source,terminal]
----
a1b2c3d4e5f67890
----

. The model files are stored on each node at the path:
+
----
/models/models/<storage_key>/
----
+
For example: `/models/models/a1b2c3d4e5f67890/`

Multiple `LocalModelCache` or `LocalModelNamespaceCache` resources that reference the same `sourceModelUri` share the same on-disk folder.
This deduplication means that the model is downloaded only once per node, even if multiple cache resources reference it.
The agent tracks each cache resource independently in its status, so deletion of one cache resource does not affect the disk storage if another cache resource with the same URI still exists.
