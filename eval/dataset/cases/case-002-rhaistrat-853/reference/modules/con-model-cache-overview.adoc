= Overview of model caching

[role="_abstract"]
You can use model caching to pre-download large language models to node-local storage, reducing inference service cold-start times from approximately 15-20 minutes to approximately 1 minute.
Model caching is especially valuable for autoscaling workloads where fast pod startup is critical to responding to traffic spikes.

Model caching introduces a persistent local-disk caching layer that downloads models to selected cluster nodes before inference services need them.
When an inference service starts, it mounts the locally cached model instead of downloading it from the remote registry, which eliminates the download delay during pod startup.

[discrete]
== Architecture components

Model caching consists of custom resource definitions (CRDs) and controller components that work together to manage the cache lifecycle.

.Custom resource definitions
The following CRDs define the model cache configuration:

`LocalModelNodeGroup`::
A cluster-scoped resource that defines a group of nodes for model caching.
Each node group specifies the storage limit, PersistentVolume (PV) template, and PersistentVolumeClaim (PVC) template for the nodes in the group.

`LocalModelCache`::
A cluster-scoped resource that defines a model to cache.
Each cache resource specifies the model URI, expected model size, and target node groups.
Models cached with this resource are available to inference services in any namespace.

`LocalModelNamespaceCache`::
A namespace-scoped resource that defines a model to cache with access restricted to inference services in the same namespace.
This resource is useful in multi-tenant environments where models should not be shared across namespaces.

`LocalModelNode`::
A cluster-scoped resource managed by the controller that tracks the download status of cached models on a specific node.
You do not create this resource directly.

.Controller components
Two controller components manage the model cache lifecycle:

LocalModel controller::
A Deployment that watches `LocalModelCache` and `LocalModelNamespaceCache` resources.
When you create a cache resource, the controller creates PV and PVC pairs for each target node and updates the `LocalModelNode` resource to trigger downloads.
The controller also reconciles inference services to inject cached model references.

LocalModelNode agent::
A DaemonSet that runs on nodes labeled with `kserve/localmodel=worker`.
The agent watches the `LocalModelNode` resource for its node and creates download jobs to fetch models to local storage.
It also deletes cached model files when a cache resource is removed.

[discrete]
== Data flow

The following sequence describes how a model moves from a remote registry to a locally cached state:

. You create a `LocalModelCache` or `LocalModelNamespaceCache` resource specifying the model URI and target node groups.
. The LocalModel controller creates PV and PVC pairs for each target node in the specified node groups.
. The controller updates the `LocalModelNode` resource on each target node with the model information.
. The LocalModelNode agent on each node detects the new model entry and creates a download job.
. The download job fetches the model from the remote registry and stores it on the node's local disk.
. The agent updates the `LocalModelNode` status to reflect the download progress.
. The controller aggregates the per-node status into the cache resource's `nodeStatus` and `copies` fields.
. When you create an `InferenceService` or `LLMInferenceService` with a `storageUri` matching the cached model, a mutating webhook automatically configures the inference service to mount the local PVC instead of downloading the model at startup.

[discrete]
== Cluster-scoped and namespace-scoped caches

Model caching supports two scoping models:

Cluster-scoped (`LocalModelCache`)::
The cached model is available to inference services in any namespace.
The `sourceModelUri` must be unique across all `LocalModelCache` resources in the cluster.
PVs created for cluster-scoped caches use owner references for automatic garbage collection during deletion.

Namespace-scoped (`LocalModelNamespaceCache`)::
The cached model is available only to inference services in the same namespace as the cache resource.
This scoping model supports multi-tenant environments where model isolation between namespaces is required.
PVs created for namespace-scoped caches cannot use owner references due to a Kubernetes limitation and are explicitly deleted during cleanup.
