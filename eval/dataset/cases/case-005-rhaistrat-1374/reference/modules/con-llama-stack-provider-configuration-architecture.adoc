= Llama Stack provider configuration architecture

[role="_abstract"]
You can configure which API providers are active in your Llama Stack server by understanding the two-file provider architecture.
The Llama Stack distribution image uses a `build.yaml` file as the complete provider manifest and a `config.yaml` file as the runtime configuration subset.
Knowing how these files relate helps you choose the right providers for your deployment and re-enable providers that are not included in the default runtime configuration.

The Llama Stack distribution image includes a build-time provider manifest (`build.yaml`) and an autogenerated runtime configuration (`config.yaml`).
The `build.yaml` file is the source of truth for all provider definitions.
The `config.yaml` file is a subset of `build.yaml`, generated by the build system to include only the providers recommended for production use.

[NOTE]
====
The `build.yaml` file is used during image build and is not included in the final container image.
Only `config.yaml` is copied into the image.
The provider definitions from `build.yaml` are provided in the re-enablement procedure for reference.
====

[discrete]
== How the build system generates the runtime configuration

During the image build process, a build script reads the `build.yaml` manifest and removes specific provider types from the generated `config.yaml`.
The build system maintains a list of provider types to exclude from the generated runtime configuration.
The following inline providers are excluded:

* `inline::sentence-transformers`
* `inline::milvus`
* `inline::faiss`

The generated `config.yaml` includes a header comment that lists the stripped provider types for reference:

[source,yaml]
----
# This file is automatically generated from build.yaml
# by distribution/build.py - do not edit manually.
#
# Stripped provider types (dependency only - available via custom config.yaml):
#   - inline::faiss
#   - inline::milvus
#   - inline::sentence-transformers
----

The Python dependencies for these providers remain pre-installed in the container image.
Only the provider definitions are removed from the default runtime configuration.

[discrete]
== Dependency-only providers

Providers that are stripped from the default `config.yaml` are classified as _dependency-only_ providers.
This category means that the provider's Python packages are installed in the container image, but the provider is not activated unless you supply a custom `config.yaml` at runtime that includes the provider definition.

The following table summarizes the provider categories in the Llama Stack distribution image:

.Provider categories
[cols="1,2,2", options="header"]
|===
|Category
|Behavior
|Examples

|Enabled by default
|Included in the default `config.yaml` and activated at server startup without additional configuration.
|`inline::localfs`, `inline::builtin`, `inline::file-search`, `inline::pypdf`, `inline::reference`

|Environment-variable-activated
|Included in the default `config.yaml` but only activated when the corresponding environment variable is set.
|`remote::vllm` (requires `VLLM_URL`), `remote::milvus` (requires `MILVUS_ENDPOINT`)

|Dependency only
|Stripped from the default `config.yaml`. Dependencies are pre-installed but the provider requires a custom `config.yaml` to activate.
|`inline::sentence-transformers`, `inline::milvus`, `inline::faiss`
|===

[discrete]
== Why inline providers were removed from the default configuration

The default runtime configuration is optimized for production deployments.
Inline providers run within the Llama Stack server process, which introduces the following limitations:

* **Scalability**: `inline::milvus` is incompatible with multi-worker deployments because it uses a local database file that cannot be shared across workers.
* **Resource isolation**: Inline embedding providers such as `inline::sentence-transformers` consume GPU or CPU resources within the server process, competing with inference workloads.
* **Production readiness**: Remote providers such as `remote::vllm` and `remote::milvus` run as independently scaled services, providing better fault isolation and resource management.

By removing inline providers from the default configuration, the distribution image steers deployments toward remote provider options that are suitable for production workloads.

[discrete]
== Retained inline providers

The following inline providers remain in the default `config.yaml` because they are runtime dependencies of core Llama Stack features:

* `inline::localfs` -- Required by the `inline::file-search` tool runtime provider. Provides local file storage for the files API.
* `inline::file-search` -- Provides the built-in retrieval-augmented generation (RAG) file search tool. Depends on `inline::localfs` at runtime.
* `inline::builtin` -- Provides the responses API implementation.
* `inline::pypdf` -- Provides PDF file processing.
* `inline::reference` -- Provides the batches API implementation.

[IMPORTANT]
====
The `inline::localfs` provider is not affected by the inline provider removal.
Do not add `inline::localfs` to the stripped provider list without also removing `inline::file-search`, because `inline::file-search` requires a files provider at runtime.
====

[discrete]
== Phase 2: Full dependency removal

In a future release, the Python dependencies for the dependency-only providers will be fully removed from the container image.
After Phase 2, supplying a custom `config.yaml` that references `inline::sentence-transformers`, `inline::milvus`, or `inline::faiss` will fail because the required Python packages will no longer be pre-installed.

Plan your migration to remote provider options before Phase 2 takes effect.
For the recommended remote provider replacements, see xref:llama-stack-api-provider-support_{context}[].
