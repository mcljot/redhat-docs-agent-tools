= Re-enable dependency-only inline providers by using a custom config.yaml

[role="_abstract"]
You can re-enable inline providers that were removed from the default Llama Stack runtime configuration by supplying a custom `config.yaml` file at server startup.
This procedure provides a temporary workaround while you migrate to remote provider options for production deployments.

[IMPORTANT]
====
Re-enabling inline providers is a temporary workaround.
In a future release, the Python dependencies for dependency-only providers will be fully removed from the container image.
Red Hat recommends migrating to remote provider options for production deployments.
See xref:llama-stack-api-provider-support_{context}[] for the recommended remote providers.
====

.Prerequisites

* A Llama Stack distribution image based on {product-name} {product-version} or later is available.
* You have identified which dependency-only providers your deployment requires. For a list of dependency-only providers, see xref:llama-stack-provider-configuration-architecture_{context}[].
* You have access to the default `config.yaml` from the container image. The full provider definitions are provided in step 2 of this procedure.

.Procedure

. Identify the inline provider definitions that your deployment requires.
+
The following providers are available as dependency-only providers in the container image:
+
--
`inline::sentence-transformers`:: Provides local embedding inference. Use this provider if you do not have access to an external embedding service.
`inline::milvus`:: Provides a local Milvus vector database by using a file-based storage backend. Incompatible with multi-worker deployments.
`inline::faiss`:: Provides a local Facebook AI Similarity Search (FAISS) vector store for similarity search.
--

. Create a custom `config.yaml` file that includes the provider definitions for the providers you need.
+
Start with the default `config.yaml` from the container image as a base.
The default `config.yaml` is a complete, valid configuration file.
Add the provider definition blocks for the dependency-only providers you identified in the earlier step.
+
The following examples show the provider definitions for each dependency-only provider.
+
To add `inline::sentence-transformers` to the `inference` API, include the following block under `providers.inference`:
+
[source,yaml]
----
  - provider_id: sentence-transformers
    provider_type: inline::sentence-transformers
    config: {}
----
+
To add `inline::milvus` to the `vector_io` API, include the following block under `providers.vector_io`:
+
[source,yaml]
----
  - provider_id: milvus
    provider_type: inline::milvus
    config:
      db_path: /opt/app-root/src/.ogx/distributions/rh/milvus.db
      persistence:
        backend: kv_default
        namespace: vector_io::milvus
----
+
[NOTE]
====
The `db_path` value must point to a writable location inside the container.
The default path matches the container image's filesystem layout.
If you change this path, ensure the directory exists and is writable.
====
+
[WARNING]
====
The `inline::milvus` provider is incompatible with multi-worker deployments because it uses a local database file that cannot be shared across workers.
Use `remote::milvus` for multi-worker environments.
====
+
To add `inline::faiss` to the `vector_io` API, include the following block under `providers.vector_io`:
+
[source,yaml]
----
  - provider_id: faiss
    provider_type: inline::faiss
    config:
      persistence:
        backend: kv_default
        namespace: vector_io::faiss
----

. Start your Llama Stack server with the custom `config.yaml` file.
+
The method depends on how you run your Llama Stack server.
+
.. *Standalone container*: Mount the custom `config.yaml` file into the container and set the `RUN_CONFIG_PATH` environment variable to the path inside the container.
+
In the following command, replace `<path_on_host>` with the absolute path to your custom `config.yaml` file on the host, and replace `<path_in_container>` with the target path inside the container:
+
[source,terminal]
----
$ podman run \
  -p 8321:8321 \
  -v <path_on_host>:<path_in_container> \
  -e RUN_CONFIG_PATH=<path_in_container> \
  quay.io/opendatahub/odh-ogx-core:<tag>
----
+
.. *{product-name} operator*: Pass the custom `config.yaml` through the `LlamaStackDistribution` custom resource.
For the exact custom resource field and method, see the {product-name} operator documentation for your version.

. Verify that the Llama Stack server starts and the expected providers are registered.
+
Check the server logs for provider registration messages.
Each re-enabled provider should appear in the startup output.

.Verification

* Verify that the server is running and healthy:
+
[source,terminal]
----
$ curl http://localhost:8321/v1/health
----
+
The expected output is:
+
[source,json]
----
{"status":"OK"}
----

* Verify that the re-enabled providers are registered by checking the server startup logs:
+
[source,terminal]
----
$ podman logs <container_name>
----
+
In the preceding command, replace `<container_name>` with the name or ID of your Llama Stack container.
The logs show a registration message for each provider that is successfully activated.
Look for lines that contain the provider type and a successful registration status, for example:
+
[source,terminal]
----
Provider `inline::sentence-transformers` registered for API `inference`
----

* If you re-enabled `inline::sentence-transformers`, verify that the embedding model is displayed in the model list:
+
[source,terminal]
----
$ curl http://localhost:8321/v1/models
----
+
The output includes an entry for the embedding model registered with the `sentence-transformers` provider.

.Troubleshooting

If the server fails to start after you provide a custom `config.yaml`, check the container logs for the following common errors:

* *YAML syntax error*: The server fails to parse the configuration file.
Verify that the YAML syntax is valid and that indentation is correct.
* *Provider type not registered*: The server does not recognize a provider type in the configuration.
Verify that the `provider_type` value matches a supported provider exactly (for example, `inline::sentence-transformers`, not `sentence-transformers`).
* *Python `ImportError` at startup*: A required Python dependency is not installed in the container image.
This error occurs if the Python dependencies for dependency-only providers have been removed in a later release.

[NOTE]
====
In disconnected environments where remote provider services are not reachable, re-enabling inline providers through a custom `config.yaml` is a viable approach.
The Python dependencies for inline providers remain pre-installed in the container image for this release.
====
